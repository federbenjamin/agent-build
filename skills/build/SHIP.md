# /build — SHIP

**Ship only when shipping is the goal.** When the operator's goal for the work is a test, a comparison, or "get X working", stop after CLOSE and hold every unit locally until the result is in and the operator says ship — a finished unit is not a ship signal. When the last unit's CLOSE ends under such a hold, fire `node ~/.agent-build/runtime/buildEvent.ts finished --runid '<runid>' --outcome unmerged` (no `--pr`: nothing was pushed).

**Run the gate from the run tree's top folder** (CLOSE §Trees): it takes the repo from the cwd and the base from the ledger's `freshen:` line. A stacked unit whose `freshen:` line names its parent's head passes `--base origin/main` to every gate and `stagePlan.ts` call here (SKILL §Multi-unit plans). **A `the signals arm could not run here (…) — re-run outside the sandbox` line** (the gate exits 2 with it) means the repo's signals arm failed (any failure but an old arm's exit 2; most often a sandbox refusal): re-run that same command with `dangerouslyDisableSandbox: true` (CLOSE, top). Key on the line, not the exit code; it is never a verdict.

**Every ledger line this stop writes** (`ship:`, `drift-merge:`, a late `hand-test-<n>:`) goes through `ledgerLine.ts`, never typed into `ship.md` (CLOSE §The steps).

1. **Merge main, `<checks>`, then `<push>` once.** `git fetch origin`, then run the gate (step 3's command) and read it only for main's drift (it also fails here on the `ship:` line not yet written). A line saying `origin/main` advanced on this branch's files after the wave means **Main drift. A run has at most one drift group.** The first time, read `DRIFT.md` in full and run it (its first step notes the pre-merge head and merges main), so its fixes ride the same push, then re-run the gate. Any later move is only merged, with no reader: note the head (`git rev-parse HEAD`, its own call), merge `origin/main` (conflict → resolve per hunk), write `drift-merge: | from=<head before the merge> | sha=<head after the merge>`, then re-run the gate; the `<checks>` run below is its run. With no drift, merge `origin/main` (conflict → resolve per hunk), so a conflict surfaces before the push. Then run the `<checks>` step — the whole pre-push run; the `<push>` step runs every other check (a push red on a check arm is your defect); red → fix and re-run, never push past it. Then the `<push>` step, bare, in the background (draft the PR body while it runs), never wrapped or `--no-verify` — a repo's push command may heal what it can and commit that; a refusal prints its report, and the run fixes the cause, re-runs only the arm that failed, and pushes again. Then `<pr_open>` (the notes carry the repo's title, type, class, and body flags, or the skill it uses) — or, when the PR exists (a banked run's draft), `gh pr edit <n> --body-file <file>`, so a question answered since leaves its `## Open questions` — the body carrying the brief's checklist, the class moment from `<run-dir>/class-moment.txt` (BRIEF step 4) — its `summary` and `impact` are the `## What it does` text, and its `class:` line followed by its `decisions:` lines, verbatim with their source tags, are a `## Decisions` section placed directly before `## Open questions` (one reader's two lists: what was decided for the operator, and what could not be; the class line keeps its `(agent, unconfirmed)` or `(operator)` so the PR says whether anyone has vetoed it; `size`, `signals`, `model` stay in the ledger; `metrics` goes to `## Proven by` when it is not `none`) — the open `## Q<n>` entries (a heading with no `(answered …)`) of the question bank `<run-root>/<worktree>-<branch>/afk-questions.md` (CLOSE 4a), when it exists, under `## Open questions` — the leftovers lines when the run has no tracker (CLOSE step 13), and the ticket link when a ticket covers the work. Ledger: `ship: <pr-url> | sha=<head>` — the head the marker names.

   **A commit after the final table** — the push's own heal commit, your fix for a red check or a conflict — owes no hand test: a claim that passed stays passed, and the push's checks carry the change. When you judge the change reaches a claim, you may spawn a fresh `hand-tester` on it, as CLOSE step 5 does, with its `hand-test-<n>:` line (after `ship:` is fine: the ledger's order carries no meaning past its first two lines); once its file is in, re-run `node ~/.agent-build/runtime/reviewTable.ts build --run-dir <run-dir> --round final` — the final table reads that hand-test file, so a table built before it is stale. Then the marker and the gate.

2. **Marker**, built by the emitter, never by hand, posted only on exit 0 and never piped (`<head>` is the sha `git rev-parse HEAD` printed, run as its own call). First `node ~/.agent-build/runtime/shipGate.ts --ledger <run-dir>/ship.md --print-checks`: it runs the whole gate and, only on a pass, prints one line of the `--check <name>=PASS|N/A` flags this run's marker owes (`freshen`, `wave`, `fix`, `confirm`, `hand-test`, `verifier`); on a fail it prints the failures and no flags, and step 3's rules apply. Copy the flags, as printed, into:
   ```
   node ~/.agent-build/runtime/emitMarker.ts gate-clean --sha <head> --provenance "<builder@… · fixer@… · reader@… · …>" \
     --class R<n> --security "<disposition>" [--security-return <run-dir>/security-review.md] \
     <the --check flags --print-checks printed> > <inputs-dir>/marker.md
   gh pr comment <n> --body-file <inputs-dir>/marker.md
   ```
3. `node ~/.agent-build/runtime/shipGate.ts --ledger <run-dir>/ship.md` — exit 0 = merge; 1 = the run does not ship yet (each failure line names its fix); 2 = an unreadable ledger, a usage error, or a fact it could not compute here (the signals line above), which refuses the same way. Never merge past a non-zero exit by reasoning about the check.
4. `node ~/.agent-build/runtime/checkMergeEligibility.ts <pr> --ledger <run-dir>/ship.md` — re-reads the marker as a persisted comment and checks it against the marker checks the run owes, which it takes from the ledger and run dir by the gate's own rule.
5. **Merge — at every class once the ship gate is green**, with the `<merge>` step (the notes may name the repo's merge skill: ready, auto-merge, watch; relay which ending it reached). The notification names the class (and `unconfirmed` when it was), any banked ids, any open questions, and the leftovers ticket. Once the PR has merged (`gh pr view <n> --json mergeCommit` gives the merge sha):
   - **The launcher's events** (README §Build events): `node ~/.agent-build/runtime/buildEvent.ts unit-merged --runid '<runid>' --id '<unit id>' --pr '<n>'`, the unit id BRIEF step 6's `plan` event gave it; then, when this was the session's last unit, `node ~/.agent-build/runtime/buildEvent.ts finished --runid '<runid>' --outcome merged --pr '<n>'`.
   - **A public repo** (BRIEF step 6): push the store, `git -C <store> push`. A rejected push is `git -C <store> pull --no-rebase`, then the push again.
   - **The batch branch** (BRIEF §Small work): when a session log is configured, flip its session-log Todo line (`- [ ] [<batch branch>] batch: ship …`) to `[x]` before the prune below.
   - Prune the session log, only when a session log is configured ($SESSION_LOGS_DIR is set): `node ~/.agent-build/runtime/sessionLogPrune.ts --branch <branch> --pr <n> --sha <merge sha>`, which finds every log carrying `[<branch>]` lines. It moves this build's `[<branch>]` Work-log lines, its `[x]` Todo lines, and every Decisions line a later line `replaces:` into `<session-id>.archive.md` beside the log, and appends one `[<branch>] merged #<n>` line. Run it even when the `<merge>` step's watcher already ran it on `merged`: a second run is safe (it never writes a second merged line), and it moves the Todo line flipped above.
   - `git worktree remove` every part's worktree and every fixer's worktree — on a run that merges, this is the one place they go, because the handoff notes live in the parts' — and, when still standing, the writers' tree, each `db` writer's tree, every review tree, and every `build-verifier` or `simplifier` tree (`--force` for these: CLOSE §Trees). A run still banked never merges: its trees go at CLOSE step 12.
   - **The run tree**, when it is not the launch tree: `EnterWorktree` (`path`) into another tree, then `git worktree remove` the run tree (leave its local stack: its lease watcher stops it). The launch tree may take the next run by `git switch` once no agent of this run is live (CLOSE §Trees).
   - **The run's branches**, after the removals: `~/.agent-build/runtime/git-delete-merged.sh <branch> <each removed tree's branch>` (`git worktree list` names them before the removals). It deletes only a branch that main or the merged PR holds, and reports one it keeps; a kept branch is not an error to fix.
