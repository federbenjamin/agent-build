# /build — CLOSE — the wave, three fix rounds, the reads and hand tests between them, in the run's tree

**Trees.** Each open run has its own tree, which you enter before acting for that run; each read has its own review tree; and no commit or merge lands in a run tree while that run's hand tester is live (§Trees). Wait for every reader and the hand tester of a stage before the next table.

**Your only code edits here:** a fix for a red push check, a merge conflict, a floor-check change (BRIEF step 1), and the fixes of UNBANK.md. You read each agent's one-line report and each script's output, never a reader file (SKILL, top).

**Every command below runs from the run's tree** (§Trees), and every agent you spawn here is armed on the watch at spawn, in the background, with SKILL's exit handling (a stopped fixer: 4d). A part builder still running from BUILD keeps its `--part-files` entry (BUILD step 8).

**A signals arm that could not run.** `stagePlan.ts` (exit 1) and the ship gate at SHIP (exit 2) print a "the signals arm could not run here … re-run outside the sandbox" line when the repo's signals arm failed: it could not start, was killed or timed out, or exited non-zero with any code but 2 (most often a sandbox refusal). Re-run that same command with `dangerouslyDisableSandbox: true`; the same line outside the sandbox is a broken arm, a blocker to fix. Never go on from a fallback the script did not print. A `signals: <note>` line under a plan is a fallback it chose on purpose (no signals step, or an old arm's exit 2), and is fine.

## The launcher's events

Wherever this stop says the operator is told, or the run banks, fire `blocked`, the unit id being the one BRIEF step 6's `plan` event gave it (the contract: README §Build events):

```
node ~/.agent-build/runtime/buildEvent.ts blocked --runid '<runid>' --id '<unit id>' --needs '<what the operator must do>'
```

When that bank ends the session's last unit (nothing left to build or ship), fire `finished` instead, with the draft PR's number when one was opened:

```
node ~/.agent-build/runtime/buildEvent.ts finished --runid '<runid>' --outcome unmerged [--pr '<n>']
```

## Trees

**Run trees.** A run tree holds one run's branch from the run's first commit until its SHIP step 5 ends, and its branch never changes in that time. The launch tree (the one the session started in) holds the first open run. A run opened while the launch tree is held gets its own tree, `<main checkout>/.claude/worktrees/run-<branch-slug>`: from the tree you are in, `git worktree add <that path> -b <branch> <start>` with the sandbox off (`dangerouslyDisableSandbox: true`; the sandbox refuses the new folder, and a refused sandboxed try can still leave the branch behind — then run `git worktree add <that path> <branch>`, without `-b`); then `EnterWorktree` with `path: <that path>`; then the `<install>` step; then the notes' stack setup when the unit touches the database. `<start>` is `origin/main`, or for a stacked unit N the head of N-1 (SKILL §Multi-unit plans); either way the unit's brief is the new branch's first commit.

- **Move between trees only with the harness's worktree tools.** Into a run tree: `EnterWorktree` with its `path`. Back to the launch tree: `EnterWorktree` with its `path` when it sits under `.claude/worktrees/`, else `ExitWorktree` with `action: "keep"` (never `"remove"`). The harness then lets you write only in the tree you entered, so a write meant for another run is refused instead of landing on the wrong branch.
- **Never run git in another tree by `git -C <tree>` or `cd <tree> && git …`, even to read.** The harness refuses it, and in auto mode that refusal has gone on to refuse even plain commands for several turns. From your own tree, name the other branch (`git log -3 <branch>`), read the other tree's files with `ls` or `cat`, and enter the tree to act in it.
- **You are always in the tree of the run you act for.** Enter a run's tree before any git write, script, or un-isolated spawn for that run. The first call after entering, and after any compaction, is `git rev-parse --abbrev-ref HEAD`, as its own call: it must print the run's branch (the `branch=` on its `freshen:` line, once step 1 wrote it). `reviewTable.ts build`, `stagePlan.ts`, and `shipGate.ts` refuse a tree on another branch with exit 2: `run <runid> is on <b>; this tree is on <c> — enter the run's tree first`.
- Isolated spawns (builder parts, fixers, DB writers, and the two isolated readers below) are cut from the entered tree's HEAD, and each still checks the start commit its dispatch names.
- After a run's SHIP, enter another tree and `git worktree remove` the run tree from there. The launch tree may then take a new run by `git switch` to a new branch — the one branch switch left, made only when no agent of the old run is live.
- SHIP runs one run at a time, in merge order (SKILL §Multi-unit plans): stacked units need the order, and two push gates at once double the machine's load. Two runs' CLOSE may overlap.

**Review trees.** Readers never read a run tree: each read gets its own.

- **One review tree per read:** the wave, each stage read after a fix (steps 5, 8, 10, 11), the drift read and its confirm (DRIFT.md), the unbank read (UNBANK.md), and each Sonnet stand-in after a failed Codex read (§Codex fails at a read). Before the read's spawns, from the run tree: `git worktree add --detach <inputs-dir>/review-<stage>-<n> <range end>`. `<stage>` is the read's stage (`wave`, `confirm-1`, `drift-1`, …); `<n>` counts that stage's reads (1, then 2 for a stand-in); `<range end>` is the head the read reads (the wave's head; stagePlan's printed range end after a fix). A sandbox refusal → re-run that one command sandbox-off.
- Every Claude reader's dispatch names that tree, absolute, as its read root; Codex gets it as `--tree`.
- **`build-verifier` and `simplifier` spawn with `isolation: "worktree"` instead**, because they run the repo's own commands (the `<manifest>` step, a repo budget re-measure (the notes name it)), which read cwd. Their dispatch names `start commit: <range end>` in place of a read root; each checks its HEAD against it and runs `<install>` before its first repo command. When each reports, remove its tree: `git worktree remove --force <its path, from the spawn's result>` (an installed tree is not unchanged, so the harness keeps it).
- Remove the review tree (`git worktree remove --force <inputs-dir>/review-<stage>-<n>`) once every reader of that read has reported and its Codex run has exited. Step 12's banked cleanup and SHIP step 5 remove any still standing.

**The hand tester pins its run tree.** It runs un-isolated in the run tree, because the stack and simulator it drives serve that tree's files. No commit or merge in a run tree while that run's hand tester is live. The check, before each commit or merge there, is the harness's live-agent check when it has one, asked for live `hand-tester` agents whose cwd is the run tree; it prints one line per live match (`<agent id> <type> <cwd>`). Empty output and exit 0 is clear; any line, or any non-zero exit, counts as live. A record that names no tree matches every tree. With no such check, the hand tester is live from its spawn until its report (`hand-test-<n>.txt written` or `blocked:`) is in.

**The stack rule, per run tree.** Nothing changes a run's stack — the notes' stack start, a migration, a reset, an edge-runtime restart — while anything uses it: that run's hand tester (the `--live` check), a DB writer's verify run (BUILD), or step 4e's `<db_gate>` run (you started each of the last two: wait for its exit). After any merge that changes a schema file the notes name — a part, the freshen, a fixer — run the notes' stack refresh before the next DB writer's verify, `<db_gate>` run, or hand tester. A run's stack only moves forward, because its tree's branch never switches; a merge that edits an already-applied migration owes the notes' reset instead.

## The readers

The class decides the wave's readers (`RISK_CLASS_READERS`, `~/.agent-build/runtime/lib/riskClass.ts`, the single authority). Before you add a reader, a check, or a run that this file does not call for, read the decision principles your instructions name, if any. The table:

| Class     | Readers                                                                                                                       |
| --------- | ----------------------------------------------------------------------------------------------------------------------------- |
| R0        | `review-cursory`                                                                                                              |
| R1        | `review-cursory`, `gate-silent-failure-hunter`                                                                                |
| R2        | + `security-review` (exploit level)                                                                                           |
| _(every)_ | `build-verifier` — it fires by brief BREADTH, not by class; it never sits out, and only a `--from-branch` run has no verifier |
| _(every)_ | `simplifier` — it fires by SIZE or by CONTENT, not by class; see the trigger rule below                                       |

**The `simplifier` is selected by SIZE or by CONTENT, at every class.** `<size> --diff-file <it> --class R<n> --pair-min-size <codex_pair_min_size> --pair-min-class <codex_pair_min_class>` (`CODEX_PAIR_MIN_SIZE` and `CODEX_PAIR_MIN_CLASS` (SKILL Setup 2), or a session contract's values when it sets them) prints three verdict lines and the wave reads them, never comparing numbers by hand: the size line `[<bucket>] <n> counted lines … · <dirs>` (the bucket is the PR title's size label when the repo uses one); `simplifier: fires (<n> ≥ <floor>)`, `simplifier: fires (…; content — …)`, or `simplifier: sits out (<n> < <floor>)` — by SIZE at or above `SIMPLIFIER_TRIGGER_MIN_BUCKET`, or by the repo's CONTENT trigger at any size when its size step has one (the notes say what it is and which hunk to hand the spawn as a focus hint); and the `codex pair:` line (below). It is deliberately absent from `RISK_CLASS_READERS`, so the gate owes no line for it. **A repo's size step may also print repo reader lines**, `reader: <agent> — fires (<why>)` or `reader: <agent> — sits out (<why>)`: spawn each firing agent (a repo agent the notes name) in the wave with the standard reader inputs and output `<run-dir>/<agent>.md`, and record it on the `wave:` line after the first `|` as `repo: <agent>` — the gate owes no line for it, and telemetry reads its file through that segment (`parseWaveLine`, `~/.agent-build/runtime/lib/riskClass.ts`).

**Except for the simplifier selection above, size only lets a reader sit out; it never changes the class set:** `gate-silent-failure-hunter` sits out under `WAVE_HUNTER_MIN_LINES` when no hunk contains `catch`, `await`, or `Promise`; `build-verifier` never sits out — it reads every run that has a brief, at every class, and `--from-branch` has no verifier at all because it has no brief; above `WAVE_CURSORY_SPLIT_LINES` cursory runs as two spawns with exclusive file slices, cut at the folder boundary that comes closest to half the counted lines: `node ~/.agent-build/runtime/cursorySplit.ts --diff-file <inputs-dir>/diff.patch` prints every folder's counted lines (the `<size>` step's own count, one run per file; run it outside the sandbox when that step is `tsx`) and a `cut: slice 1 = <folder>/ (<n>) · slice 2 = the rest (<m>)` line — slice 1 is that folder, slice 2 every other file. `review-cursory` and `security-review` never sit out. Every skip prints `skipped: <reader> — <threshold>`. The `SUBAGENT_MAX` cap (SKILL Setup 2) holds the Claude readers alive at once, and `CODEX_MAX` the Codex runs; the two pools are counted apart, so every Codex run starts in the first beat, beside the first Claude readers. A wave larger than the cap runs in beats, as many as it takes: one message spawns each beat's readers, and the next beat starts as the last one's slots free. The Claude beats take the readers in this order: the class readers first, then `build-verifier`, the `simplifier`, and the repo readers.

**Id prefixes.** Each reader's finding ids are `<PREFIX>.<n>`; give each spawn its prefix, exactly as this table writes it. The table script gives a stage row back to the reader whose prefix it holds, and `reviewTable.ts check` and `build` refuse a global reader's file that uses another prefix (`READER_ID_PREFIX`, `~/.agent-build/runtime/lib/runFiles.ts`).

| Reader | Id prefix |
| -- | -- |
| `review-cursory` | `CURSORY` |
| `review-cursory-codex` | `CODEX` |
| `gate-silent-failure-hunter` | `HUNTER` |
| `security-review` | `SEC` |
| `build-verifier` | `VERIFIER` |
| `simplifier` | `SIMP` |
| a repo reader | its own — the notes name it |
| `session.md` | `SESSION` |
| a hand-test `fail (code)` | `HAND` — the table makes the row |

Slice `k` of a split read, from the second slice on, adds `-<k>` to its prefix (`CURSORY-2`, `CODEX-2`); the first slice keeps the plain one. A Sonnet `review-cursory` standing in for a failed Codex read at a stage writes `CURSORY`.

**After a fix, a reader runs at a stage only when it can find a kind still fixed there.** `node ~/.agent-build/runtime/stagePlan.ts` prints, per stage, each reader as `owed`, `sits out`, or `not owed`, with the reason; spawn exactly the owed ones. The gate computes the same verdicts (`planStage`, `~/.agent-build/runtime/lib/owed.ts`), so a reader you skip that it owes fails the ship. One verdict needs you: a `build-verifier` line ending `run <manifest> --brief-file <brief> --no-exercise yourself` — run that command on the post-round head; a non-zero exit owes the verifier at that read.

## The run files

Every reader, the fixer, and the hand tester writes one grammar, owned by `~/.agent-build/runtime/lib/runFiles.ts`; the ledger's is `~/.agent-build/runtime/lib/ledger.ts`. `node ~/.agent-build/runtime/reviewTable.ts check --file <file> --stage <stage> [--run-dir <run-dir>]` checks any one of them (`--stage`: `wave`, a stage name, `session`, `fix-<round>`, or `hand-test`; a drift group's own `drift-<g>`, `drift-confirm-<g>`, or `fix-drift-<g>`, which `--run-dir` needs; exit 0 valid, 1 invalid with one `line <n>: <error>` each). Each agent runs it on its own file; you run it on each Codex output and on `session.md`.

- **Wave reader files** `<run-dir>/<reader>.md` (`<reader>-<n>.md` per slice): finding blocks in the `review-cursory` agent's §Rubric — `locator`, `kind`, `finding`, `after`, and an optional `invariant`/`vacuity` pair — ids `<PREFIX>.<n>` in `0`–`99`. Slice `k` from the second on adds `-<k>` to its prefix (`CURSORY-2.1`, `CODEX-2.1`).
- **Stage files** `<run-dir>/stage-<stage>/<reader>.md` (drift group `<g>`: `stage-drift-<g>/`, `stage-drift-confirm-<g>/`): `## Status` (one line per row the reader was given, or `- none`), then `## New` (finding blocks in the stage's id range, or a `NO FINDINGS` line); `build-verifier`'s ends with its `VERDICT:` line.
- **`session.md`** — findings that come from no reader, each a block with ids `SESSION.<n>` (unique in the file) and a `stage:` line naming the stage whose round takes it (`wave`, `confirm-1`, `confirm-2`, `last`, `escalate`, `drift`, `drift-confirm`). You write them: the known items a dispatch used to list, the builder's `out-of-lane candidates:` entries, a test writer's red test that indicts the code (BUILD), and anything you learn yourself. Telemetry never counts `SESSION` as a reader. Check the file after each edit with `--stage session`.

```finding-block
### SESSION.1 — the writer's W2 test fails: the queue keeps a row for the wrong user
- locator: packages/core/src/queue/pending.ts:88
- kind: behavior
- stage: wave
- finding: test pendingQueue.test.ts "scopes by user" fails; the filter drops the user id.
- after: the queue returns only the caller's rows; the W2 test passes.
```

- **`table.json`**, `table-<round>.md`, and the leftovers list — written only by `reviewTable.ts build`, never by hand. `table-<round>.md` is the fixer's; you never read it.
- **`fix-<round>.txt`** (the fixer), **`hand-test-<n>.txt`** and `hand-test-<n>/H<k>.out` (the hand tester), and `extra-sources.json` (you, step 14).

**A round's rows** are what its fixer gets. Each round fixes only some kinds (`STAGES_FIXING`, `~/.agent-build/runtime/lib/runFiles.ts`): round 1 every kind, round 2 all but `test-tool`, `dev-tool`, and `text`, and round 3, escalate, and `drift-<g>` only `behavior`, `security`, and `missing`; the rest go to the leftovers ticket. The table merges findings on one place, applies the target-file label rules, routes each prior row by the fixer's line and the stage's answers, and turns each hand-test `fail (code)` on claim `H<k>` into row `HAND.<k>`, kind `behavior`. A fixer's `fixed · kind=<lower kind>` whose read comes back `unresolved` keeps the row's old kind. A finding that predates the PR, or is independent of it, has no special route: its kind and stage decide.

**Prose drift is fixed, never ticketed**: readers return it under `## Prose drift (advisory)` without ids, and the table script turns each line into a round-1 `text` row whose id continues that reader's numbering, so the fixer corrects the stale comment or doc in the same round as everything else. "Advisory" means only that it never blocks a ship on its own: a `text` row left unfixed after round 1 is a leftover like any other.

## The steps

Ledger lines are one `<move>: <segments>` line per move, in the order below; a `key=value` segment is a field. Every move appears once, except the drift group (DRIFT.md; at most one per build), `drift-merge:` (every one counts), `leftovers:` (the last one counts), `verifier:` (the last one counts), `banked:` (every one counts), and `answered:` (every one counts). Past the class and `flow:` lines, order carries no meaning outside a drift group — every reader of the ledger reads a move by name — so write each line when its move happens: a `banked:` line when you bank, a `verifier:` line again after a later read that owed the verifier, a SHIP-time `hand-test-<n>:` line after `ship:`. Write only move lines: any `word:` line after the class line is read as a move, so the ledger holds no prose. `<inputs-dir>` is SKILL.md's scratch folder.

**Never type a line into `ship.md`: `ledgerLine.ts` writes every one.** `node ~/.agent-build/runtime/ledgerLine.ts --ledger <run-dir>/ship.md <move> "<text segment>"… [--<key> <value>]…`, from the run's tree. Each `Ledger:` form below maps onto it one way: every `|`-separated text segment is one quoted argument, and every `key=value` field is `--key value`. `sha`, `from`, and `measured-at` take a sha, or the word `head` for the tree's HEAD (a read line's `sha=` is the range end stagePlan printed, so pass that sha). `wave: review-cursory, build-verifier | skipped: simplifier — 40 < 100 | sha=<head>` is `… ship.md wave "review-cursory, build-verifier" "skipped: simplifier — 40 < 100" --sha head`. The first call is the `class` line: it creates the file and writes `flow: 2` under it, so step 1 writes no `flow:` line of its own. A once-only move that already has a different line is refused too, and the refusal prints the standing line: `--replace <move> …` rewrites it in place (a redone step, the operator's class veto), and `--remove <move>` deletes the move's last line. A move that repeats (the list above) takes each new line under its last one: never `--replace` one to add to it. A line that already stands word for word is left alone. Calls sent side by side all land: each waits for the one before it.

1. **Freshen.** `git fetch origin`; merge `origin/main`; conflict → resolve per hunk (the notes may name a merge-audit command), or STOP. Materialize `git diff <base>...HEAD > <inputs-dir>/diff.patch` (`<base>` is the `base=` the ledger's `freshen:` line gets below); `<size> --diff-file <it> --class R<n> --pair-min-size <codex_pair_min_size> --pair-min-class <codex_pair_min_class>` (the floors as §The readers names them: `CODEX_PAIR_MIN_SIZE` and `CODEX_PAIR_MIN_CLASS`, or a session contract's values when it sets them) re-prints the three verdict lines. Then run the notes' freshen additions, if any (a repo budget ratchet (the notes name it) that must be locked in before the wave reads the size step's content trigger). An addition that commits changes what the size step reports: re-materialize `diff.patch` and re-run the size step after that commit, and read the wave's verdicts from the second run; `measured-at=` and the `freshen:` line's `sha=` name the head after it. Ledger, in this order: `class: R<n> — <who>, <date> | measured-at=<head sha>` (its call writes `flow: 2` under it); `brief: <repo-relative brief path>` (on `--from-branch`, `from-branch: <branch>` and `hand-test-block: <repo-relative path>` instead; a public repo's path is `store:briefs/<file>`, BRIEF step 6); `steps: …` (SKILL Setup 4); `build: …` (BUILD; none on `--from-branch`; on a briefed branch built before this run, entered here at CLOSE, `build: model=<the brief's model: line> | agent=none | sha=<the head you entered at>` — no builder ran in this run, so the fixer's handoff note is `none`, and the line carries no `parts=` whatever the brief holds); `freshen: <merged sha> | base=<the run's base: origin/main, or the parent PR's head for a stacked unit whose parent is unmerged> | branch=<the run's branch; on --from-branch, that branch> | sha=<head>`. Every script reads the base from `base=` (a stacked unit switches to `--base origin/main` at SHIP: SKILL §Multi-unit plans), and `reviewTable.ts build`, `stagePlan.ts`, and `shipGate.ts` check the tree's branch against `branch=` (§Trees). A freshen merge that changes a schema file the notes name owes the stack refresh (§Trees) before any hand tester or `<db_gate>` run.

2. **Wave.** One message per beat spawns the class's readers (one beat when the wave fits the live cap, §The readers). First make the wave's review tree, `<inputs-dir>/review-wave-1` at the run tree's HEAD (§Trees). Every reader gets: the diff range `<base>...HEAD`, the read root (that review tree, absolute; `build-verifier` and `simplifier` spawn with `isolation: "worktree"` and get `start commit: <the wave head>` in its place), the brief's path, its output path `<run-dir>/<reader>.md` (`<reader>-<k>.md` per slice), the stage `wave`, and its id prefix from §The readers → Id prefixes (with `-<k>` for slice `k` from the second on). Each reader reads the repo notes itself and checks its own file with `--stage wave`. Known items go to `session.md` as `SESSION` blocks, stage `wave` — never into a dispatch. The verifier runs the `<manifest>` step with `--no-exercise`; the hand tester runs the exercises later. A missing file → re-spawn that reader fresh once, then STOP. Remove the review tree, and each isolated reader's tree, when §Trees says.

   **A `review-cursory` spawn is paired with a Codex read of the same role only when the size bucket is at or above `CODEX_PAIR_MIN_SIZE` AND the class is at or above `CODEX_PAIR_MIN_CLASS` (SKILL Setup 2), and a `codex_role` step exists.** Every size step — the global fallback or a repo's own — takes both as `--pair-min-size <bucket>` / `--pair-min-class R<n>` and prints the verdict on its `codex pair:` line; always pass them, so a session override reaches the verdict. `codex pair: skipped (R0, S — needs ≥ R1 and ≥ M)`, or `codex pair: skipped (no codex_role step)` (Codex is not installed), means the one Sonnet read is the whole wave review, and the wave line records that segment after its first `|`; `codex pair: undecided — pass --class R<n>` means re-run with the pinned class. Otherwise: `<codex_role> review-cursory --tree <read-root> --dispatch <file> --out <run-dir>/review-cursory-codex.md --log <inputs-dir>/codex-wave.log`, read-only sandbox, the same brief, range, read root, and focus hints. **A Codex run has no file channel**: the dispatch tells the read that it is the paired Codex read, to use the id prefix `CODEX` (`CODEX.1`, …), and to emit the WHOLE file as its FINAL MESSAGE and write no file; `codex -o` captures that message into `--out`. **Launch every Codex run in the BACKGROUND** (`run_in_background`, sandbox-off); the task's exit notification is your wake. **Never wait on a Codex run in the foreground.** A split cursory pairs each slice (`review-cursory-codex-<n>.md`; ids `CODEX.<k>` in slice 1, `CODEX-<n>.<k>` from slice 2 on). When it finishes, run `node ~/.agent-build/runtime/reviewTable.ts check --file <its out> --stage wave`. The pairing is extra coverage, not a class reader: `RISK_CLASS_READERS` is unchanged.

   **A failed wave Codex run** — a non-zero exit, no `--out` file, or a file `check` refuses: no retry and no stand-in (the wave's Sonnet read already ran). Rename a refused file to `<name>.refused.txt`, so no round reads it, and record the pair as `codex: review-cursory (failed: <why>)` on the `wave:` line.

   Ledger: `wave: <readers> | skipped: <reader> — <threshold>, … | codex: review-cursory | repo: <agent>, … | sha=<head>` — the paired read and any repo reader are recorded after the first `|` and never join the reader list. `<readers>` names each class reader that read, and the `simplifier` when the size step's line said `fires` (the gate then owes its file; when it sat out, `skipped: simplifier — <why>`). A split read is named once — `review-cursory`, and `codex: review-cursory` for its pairs; the slice files carry the split. Then the verifier's line: `verifier: CLEAN | sha=<head it read>` when its latest file ends `VERDICT: CLEAN` (the gate reads the latest one: the wave's, else the last stage folder's). Write it once the wave's verifier is in; when a later read owes the verifier again (an `amend brief:` in its range, 4c), write a new `verifier:` line after that read — the last one counts. A file that ends `VERDICT: INCOMPLETE — <check>` is cleared one of two ways: fix what stopped the check and re-spawn the verifier fresh, once (before step 3 at the wave), or, when a hand-test claim runs that check (the manifest with its exercise), `verifier: CLEARED | by=hand-test-<n>:H<k> | sha=<head>` once that claim passed in that file. A second `INCOMPLETE` on the same check that no claim clears is a blocker, as in 3a: the PR stays draft and the operator is told; fire `blocked` (§The launcher's events).

3. **Table, round 1.** `node ~/.agent-build/runtime/reviewTable.ts build --run-dir <run-dir> --round 1`. It prints `round 1 · head <sha> · rows <n> (<kind> <k>, …) · leftovers <n> · banked <n>`, and one `refused: <file> — <error>` line per file its grammar refused (exit 1).
   - **3a. A refused file.** Re-spawn that reader once, fresh, with the error line; then re-run step 3. A second refusal is a blocker: the PR stays draft and the operator is told; fire `blocked` (§The launcher's events). A refused Codex file follows "A failed wave Codex run" above (at a stage: §Codex fails at a read).
   - **3b. Re-building a round.** `build` for a round `table.json` already holds re-builds it at the head it holds (it prints a `note:`), so its range and its fixer's commits stay its own; `--head <sha>` overrides, and `final` always takes the tree's HEAD. When the gate says a round is stale, run the commands it prints, in order.

4. **Fix round 1** (round 1 has rows). Spawn a fresh `fixer` with `model:` the owed model and `isolation: "worktree"` — never resume a fixer, and never the BUILD builder. The owed model is the brief's header `model:` line (the strongest part's); on `model: session` or `--from-branch` it is `opus` at R2 and `sonnet` below; `escalate` is always `opus`.
