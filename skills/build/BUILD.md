# /build — BUILD

A floor-check brief (`model: session`) spawns no builder: you made the edits at BRIEF step 1, which also owns its `build:` line. Go to CLOSE.

Every step here runs in the run's tree (CLOSE §Trees): you are in it for every git write, script, and spawn of this run. A brief with no `## Parts` block is one part, `P1`, that holds every deliverable and the whole `## Target files` list; everything below holds with one part.

8. **The trees, each owned by exactly one git user.** The harness worktree-isolation guard binds every subagent's git to the tree its OWN isolation names: an un-isolated agent in a second tree, and you yourself through `git -C`, cannot run git there at all. Non-git commands with their cwd in a sibling tree stay allowed.
   - **Run tree — the integration tree.** The run's branch, brief commit first (a public repo's brief is in the store, BRIEF step 6: there `<brief-commit>` below is the empty commit that records it). Every merge, every gate, and the push live here; the readers read review trees cut from it (CLOSE §Trees).
   - **Before any spawn.** Note the time, `date -u +%Y-%m-%dT%H:%M:%SZ` as its own call: it is the `build:` line's `started=` (step 10), from which CLOSE reads the wall budget (CLOSE §The budget stop). For each part and each slice, `node ~/.agent-build/runtime/briefCheck.ts <brief> --files <P<k>|W<k>> > <inputs-dir>/files-<id>.txt`; for each slice, `node ~/.agent-build/runtime/briefCheck.ts <brief> --slice W<k> > <inputs-dir>/slice-W<k>.txt`. When a slice is `db`, bring the run's stack up by the notes' `## hand-tester` procedure first: one stack for the run, which every DB writer reaches.
   - **Spawn order under the cap.** Claude builder parts and writers together stay under the `SUBAGENT_MAX` cap, and Codex runs (a Codex writer or read) under `CODEX_MAX` (SKILL Setup 2); the two pools are counted apart. Fill free slots in this order: parts whose every `after:` part has merged, the part with the most parts waiting behind it first; then `db` writers; then `plain` writers. One message per beat.
   - **Part worktrees — harness-made, one per builder part.** Spawn the `builder` agent with `model:` set to the part's `model:` line (`opus` or `sonnet`) and `isolation: "worktree"`. Its dispatch:
     ```
     brief: <repo-relative path>
     part: P<k> — <its head text>
     start commit: <the run tree's HEAD, git rev-parse HEAD as its own call>
     run dir: <run-dir>
     part files: <inputs-dir>/files-P<k>.txt
     not yours: every other part's files, and the files the notes list as rebuilt once
     [fast-forward: <start commit>]
     ```
     The builder builds its part's deliverables only, under its one lane rule (the `builder` agent's §Non-negotiables: a file no part lists is allowed and reported; a file on `not yours:` is a STOP). The base the harness cuts its tree from is `worktree.baseRef` (set once in `~/.claude/settings.json`; a repo's own `.claude/settings.json` overrides it), whose two values are `"head"` (the HEAD of the tree you are in) and `"fresh"` — and **`"fresh"` is the DEFAULT**, meaning the repo's REMOTE default branch, so an absent key silently hands the builder a tree with no brief commit in it. Confirm the key reads `"head"` before you spawn. If it does not, `git fetch origin` and merge `origin/main` into this branch first, so the start commit descends from the tree the harness cuts; take the start commit after that merge. Then add the line `fast-forward: <start commit>` to the dispatch: it authorizes `git merge --ff-only <start commit>` as the builder's first action, because the builder never moves its own branch on its own initiative. A worktree shares the repo's objects, so the builder needs no fetch. After that step (or at once, with no such line), the builder asserts `git rev-parse HEAD` equals the start commit and STOPs otherwise; a refused fast-forward is a STOP too; it never checks out the run's branch, which is checked out in the run tree. When its part touches the DB, it claims a stack per the notes.
   - **A `session` part** is yours: write it in the run tree (the floor check, BRIEF step 1) and commit it; no builder runs for it.
   - **A part that waits** (`after:`) spawns once every part it names has merged (step 10), as a fresh builder whose start commit is the run tree's HEAD after those merges.

     **A builder that STOPs must dirty its tree first, or it cannot be resumed.** The harness auto-cleans an isolated worktree that is UNCHANGED when the agent stops, and a resume then has no tree to return to — it wakes in the tree you are in, on the run's branch, which is the one place it must never write. So every STOP instruction in a builder's dispatch ends with: write `BLOCKED.md` at your worktree root saying what blocked you, THEN stop. One untracked file is enough; no commit is needed.

     **A resume answers a STOP or asks for a missing report list, and nothing else.** Once a builder has reported done, every finding goes to CLOSE's table and its `fixer`, never to a `SendMessage` resume of that builder.

   - **Writers — one per slice of the brief's `## Test slices`.** One or two tests stay with the part's builder (`tests: builder`); three or more go to `test-author` writers, started beside the builders. A writer's dispatch carries its slice excerpt (`<inputs-dir>/slice-W<k>.txt`), never the brief path, plus the phase (author, verify, fix); the writer reads the notes' `## test-author` section itself. Every dispatch says "never spawn a sub-agent or a fork" — a fork inherits the dispatch and edits the same files.
     - **A `plain` slice runs on Codex, in the build's one writers' worktree, which is git-free.** When `<codex_role>` is `(none)` (Codex is not on PATH), it runs as a Claude spawn in its own worktree instead, as a `db` slice does in every step (author, transplant, verify) but the stack, and the rest of this bullet does not apply. `git worktree add <abs-path> --detach <brief-commit>` from the run tree, then the `<install>` step there. `<codex_role> test-author --tree <abs-path> --dispatch <file> --out <file> --log <file>`. **Launch every Codex run in the BACKGROUND** (`run_in_background`, sandbox-off): the task's exit notification is your wake, and you check the `--out` file between other work. **A foreground or blocking wait on a Codex run is forbidden** — one stalled a session for its whole length. **One run per phase**, each with its own dispatch file that names the writers' tree, the excerpt, and the phase. Every path in the dispatch is absolute: the run's cwd is the writers' tree, not the run folder. The dispatch also spells out the test command: the default wrapper needs a `.dev-worktree.env` the writers' tree lacks. The run writes into `<abs-path>` and runs tests and proofs with `cd <abs-path> && <command>` — **no git command of any kind**, because a `git switch`/`stash` from there lands in the run tree.
     - **A `db` slice runs as a Claude spawn, in its own worktree.** Spawn `test-author` (its file pins its model) with `isolation: "worktree"`, one fresh spawn per phase. Its dispatch names the excerpt, the phase, and the run tree's absolute path. Its first step in each phase reaches the run's stack by the notes' copy rule (it copies the binding files the notes name from the run tree, then runs the `<install>` step); it never starts, stops, resets, or migrates the stack, and runs no git: its files stay uncommitted in its tree, which the harness therefore keeps.
   - **The watch.** Arm it at each spawn, in the background (SKILL, "Never end a turn to wait"): `~/.agent-build/runtime/agent-watchdog.sh --flags <each .output path>… --part-files <.output path>=<inputs-dir>/files-<id>.txt… --codex <writer's --log>:<writer's --out>…` — one `--part-files` per builder part (`files-P<k>.txt`) and per `db` writer (`files-W<k>.txt`), its key the agent's `.output` path exactly as typed among the paths, and one `--codex` per running Codex writer. `--part-files` needs `--flags`. The flag `FLAG <agent> off-part count=<n> limit=<m>` fires when that agent has edited `WATCH_OFF_PART_FILES` files in its tree that its list does not hold; the lane rule allows a few, so look at which files before you act (the ack is `--ack <agent>:off-part:<n>`). Exit 3 names one agent: look at it, then re-arm with the `ack:` flag it printed, or stop it, commit its WIP, and start a fresh agent with a note of what is done and what is left (a replaced builder's id joins its part's ids on the `build:` line).

   YOU are the only channel between builders and writers: a builder STOP or a brief amendment means re-running the affected writers with a delta dispatch. Poll by disk fact while doing other work.

9. **When a builder returns, read its report, not its diff** — the wave readers read the diff. A report is `done` or `blocked: <reason>`, names its part, and holds `out-of-lane fixes:`, `out-of-lane candidates:`, and the `design self-check:` block; one missing either list or the block is incomplete: resume the builder for it. Then:
   - Each `out-of-lane candidates:` entry, each `design self-check:` line that is not `none`, and each test writer's red test that indicts the code (step 10) becomes a finding block in `<run-dir>/session.md`, id `SESSION.<n>`, `stage: wave` (the example and grammar: CLOSE §The run files). The table puts it in fix round 1 by its kind; the fixer drops it with a reason when it is false. Nothing a report names is dropped silently. After each edit, `node ~/.agent-build/runtime/reviewTable.ts check --file <run-dir>/session.md --stage session` must exit 0.
   - Each doubt the builder raises about the brief is yours: one you accept is an `amend brief:` commit plus a `SESSION` block for the code it changes; one you reject is, when a session log is configured, one `[agent]` Decisions line there naming the principle that decided it, else one line appended to the `decisions:` list of `<run-dir>/class-moment.txt` (in place of `none`; a veto's rewrite keeps it), `- doubt rejected: <the doubt> (principle <n>)`, which SHIP step 1 copies into the PR body's `## Decisions`. Judge a doubt at the code, not from belief: open the `file:line` it cites, and run the tool check it names (a config validator, a type-check) before you reject it. A doubt that names a mechanism you cannot refute at the code is accepted.
   - A flag that the diff changes runtime UI behavior owes a hand-test claim on it; add one by `amend brief:` when the brief has none.

10. **Integrate — the parts, the rebuilt-once files, then the writers — and accept done. All of it happens in the run tree.**
    - **Merge each part** as it reports done: `git merge <its branch>`, then spawn the parts that waited on it (step 8). A conflict means two parts shared a file: a brief defect → STOP and amend. A merge that changes a schema file the notes name owes the notes' stack refresh before the next DB writer's verify (CLOSE §Trees, the stack rule).
    - **After the last part merges,** run each rebuild command the notes list as rebuilt once, and commit the results in one commit (its subject from the notes).
    - **The transplant.** When every writer reports done, copy each writer's exclusive slice files into the run tree — from the writers' tree for a `plain` slice, from its own tree (the spawn's result names it) for a `db` slice; the slice list IS the manifest, nothing outside it moves — and commit them with explicit paths. Then `git worktree remove --force` each `db` writer's tree.
    - **Verify: `db` slices one at a time, `plain` slices side by side.** The `db` slices share the run's one stack, and a `sql` mutation proof rewrites a function in it, so a `db` verify starts only when the last one has exited. A `plain` slice shares nothing but a tree, and the `<mutation_proof>` step rewrites files in the tree it runs in, so each `plain` verify gets its own tree cut at the integrated head (`git worktree add <writers' tree>-W<k> --detach HEAD`, `<install>` there) and re-runs its writer there with a verify dispatch naming that tree. A `db` slice: after the stack refresh a schema merge owes, a fresh isolated `test-author` spawn from the integrated head, where its files are already committed; its dispatch re-carries the excerpt and its author-phase report. A test fix copies back the same way, and each verify tree is removed once its files are copied.
    - A red test that indicts the code stays red and committed: it becomes a `SESSION` block (step 9), and the fixer's round 1 turns it green. One that indicts the brief → `amend brief:` commit, re-run the writer with a fix dispatch. Conflict at any merge → a brief defect → STOP, amend, re-run the writer with a fix dispatch.
    - **Accept done only when the `<exit_checks>` step is green AND the `<tests>` step passes in this tree after every part's merge, the rebuild commit, and the transplant, except the red tests `session.md` names and a coverage gap a `SESSION` block names** (a changed line no test can reach, such as a dead branch in production code; a `(none)` step is said, not assumed green). When the `<tests>` step's command is already one of the `<exit_checks>` step's commands, the `<tests>` step is not run again: the `<exit_checks>` run is its run. After each fix of a red check, re-run only the check that failed and the tests beside the files the fix changed, as often as it takes; the last run of each counts, and together they are the run's one accepted `<exit_checks>` run in this tree (the floor check's is the other). A later commit here — a fixer's merge, a base merge — runs only the tests beside the files it changed; SHIP's `<checks>` and the push gate cover the rest. Then remove the writers' worktree; keep every part's worktree until SHIP — the handoff notes every `fixer` reads live in them. No writers (≤2 tests per part) → the copy step is skipped and the builders' own tests are their exit.

    Ledger: `build: model=<the brief's header model: line> | agent=<every builder id> | parts=<P<k>:<model>:<ids>,…> | sha=<HEAD after the last part's merge, the rebuild commit, and the transplant> | started=<that iso>`, `<that iso>` the time step 8 noted before the first spawn. `agent=` is each id the Agent tool returned for a builder part, a replacement's after the one it replaced. `parts=` lists every part of a brief with a `## Parts` block, its ids joined by `+`, `none` for a `session` part (`parts=P1:sonnet:<id>,P2:opus:<id>+<id>,P3:session:none`); a brief with no `## Parts` block, or a run where no builder ran (`agent=none`), writes no `parts=`. CLOSE step 1 places it after `steps:`.
